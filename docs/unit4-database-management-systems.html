Unit IV – Database Management Systems

UGC NET Computer Science and Applications – Paper II

This unit covers database concepts, architecture, data modeling, SQL, normalization, transactions, database security, advanced databases, data warehousing, data mining, Big Data, Hadoop, HDFS, and NoSQL.

Part A – Database System Concepts and Architecture

1. Database and DBMS

A database is an organized collection of related data.

A Database Management System (DBMS) is software used to:

  • Create databases
  • Store data
  • Retrieve data
  • Update data
  • Delete data
  • Control access
  • Maintain consistency

Examples:

  • MySQL
  • PostgreSQL
  • Oracle Database
  • Microsoft SQL Server
  • SQLite

2. Advantages of DBMS

Important advantages:

  • Reduced data redundancy
  • Better data consistency
  • Data sharing
  • Security
  • Backup and recovery
  • Integrity enforcement
  • Concurrent access
  • Data independence

3. Data Models

A data model describes how data is represented and related.

Important data models:

  • Hierarchical model
  • Network model
  • Relational model
  • Object-oriented model
  • Object-relational model
  • NoSQL models

Hierarchical Model

Data is organized as a tree.

          Root
           |
      ------------
      |          |
    Node        Node
    /  \
 Node  Node

It mainly represents one-to-many relationships.

Network Model

Data is represented using records connected by links.

It can represent many-to-many relationships.

Relational Model

Data is represented using tables.

Example:

Student_ID Name Department
101 Arun BCA
102 Anu BBA

The relational model is based on relations, tuples, and attributes.

4. Schema and Instance

Schema

A schema is the structure or design of a database.

Example:

STUDENT(Student_ID, Name, Department, Mark)

Instance

An instance is the actual data stored in the database at a particular time.

Student_ID Name Department Mark
101 Arun BCA 85
102 Anu BBA 90

Schema vs Instance

Schema Instance
Database structure Actual data
Changes relatively rarely Changes frequently
Describes design Represents current state

5. Three-Schema Architecture

The three-schema architecture separates the database into three levels.

External Level
      |
      v
Conceptual Level
      |
      v
Internal Level
      |
      v
Physical Storage

5.1 External Level

Also called the view level.

It describes how individual users see the database.

Example:

A student may see only:

Name
Roll Number
Marks

5.2 Conceptual Level

Describes the complete logical structure of the database.

It contains:

  • Entities
  • Relationships
  • Constraints
  • Attributes

5.3 Internal Level

Describes how data is physically stored.

It deals with:

  • Files
  • Indexes
  • Storage blocks
  • Physical organization

6. Data Independence

Data independence means changing one level without requiring unnecessary changes at higher levels.

Two types:

  1. Physical data independence
  2. Logical data independence

Physical Data Independence

Changes in the internal/physical level do not require changes to the conceptual level.

Example:

Changing the storage method or adding an index.

Logical Data Independence

Changes in the conceptual schema do not require changes to external views.

Example:

Adding a new attribute while preserving existing user views.

Important Point

Physical data independence
→ Internal level changes
→ Conceptual level remains unaffected
Logical data independence
→ Conceptual level changes
→ External views remain unaffected as far as possible

  • Single-valued
  • Multi-valued
  • Derived
  • Key attribute

Cardinality describes how many entities participate in a relationship.

Common types:

  • One-to-one
  • One-to-many
  • Many-to-one
  • Many-to-many

14. Relational Model

The relational model represents data using relations or tables.

Important terms:

Relation → Table
Tuple → Row
Attribute → Column
Domain → Set of allowed values

Example:

Roll Name Mark
1 Arun 80
2 Anu 90

Here:

  • Relation = Student
  • Tuples = rows
  • Attributes = Roll, Name, Mark

15. Relational Constraints

Important constraints:

  1. Domain constraint
  2. Key constraint
  3. Entity integrity
  4. Referential integrity

Domain Constraint

An attribute must contain values from its valid domain.

Example:

Age should be numeric.

Key Constraint

A key identifies tuples uniquely.

Entity Integrity

A primary key cannot contain NULL.

Referential Integrity

A foreign key must refer to a valid referenced key value, or be NULL where permitted.

Example:

DEPARTMENT
Department_ID

STUDENT
Student_ID
Department_ID

The student’s Department_ID should correspond to an existing department.

16. Relational Database Schema

A relational schema describes the structure of relations.

Example:

STUDENT(Student_ID, Name, Department_ID, Mark)

DEPARTMENT(Department_ID, Department_Name)

Primary keys can be represented as:

STUDENT(Student_ID, Name, Department_ID, Mark)
         ^ primary key

17. Update Operations

Main relational database operations:

  1. Insert
  2. Delete
  3. Update

Insert

Adds a new tuple.

Delete

Removes a tuple.

Update

Changes existing values.

Constraint violations can occur when an operation breaks:

  • Domain constraints
  • Key constraints
  • Entity integrity
  • Referential integrity

Part C – Relational Algebra and Relational Calculus

18. Relational Algebra

Relational algebra is a procedural query language.

Important operations:

  • Selection
  • Projection
  • Union
  • Set difference
  • Cartesian product
  • Rename
  • Join
  • Intersection

Selection

Selects rows satisfying a condition.

Notation:

σ condition (R)

Example:

σ Mark > 80 (STUDENT)

means select students whose mark is greater than 80.

Projection

Selects columns.

Notation:

π attributes (R)

Example:

π Name, Mark (STUDENT)

Union

Combines tuples from two union-compatible relations.

R ∪ S

Set Difference

R - S

Returns tuples in R but not in S.

Cartesian Product

R × S

Combines every tuple of R with every tuple of S.

Rename

Rename operation is represented using:

ρ

Join

Join combines related tuples.

Common joins:

  • Theta join
  • Equi-join
  • Natural join
  • Outer join

19. Relational Calculus

Relational calculus is a non-procedural query language.

It describes what data is required, rather than how to obtain it.

Two forms:

  1. Tuple relational calculus
  2. Domain relational calculus

Relational Algebra vs Relational Calculus

Relational Algebra Relational Calculus
Procedural Non-procedural/declarative
Specifies operations Specifies desired result
Describes how Describes what

20. Codd’s Rules

E. F. Codd proposed rules for relational database systems.

Frequently examined rules include:

Rule 0

The system must manage the database entirely through relational capabilities.

Rule 1 – Information Rule

All information is represented as values in tables.

Rule 2 – Guaranteed Access

Every atomic value should be accessible through table name, primary key, and attribute name.

Rule 3 – Systematic Treatment of NULL

NULL values must be supported systematically.

Rule 4 – Dynamic Online Catalog

The database description should be represented relationally and accessible using the same language.

Rule 5 – Comprehensive Data Sublanguage

At least one relational language should support data definition, manipulation, integrity, and transaction control.

Rule 6 – View Updating

Updatable views should be updatable where theoretically possible.

Rule 7 – High-Level Insert, Update, Delete

Set-level operations should be supported.

Rule 8 – Physical Data Independence

Changes in physical storage should not affect applications.

Rule 9 – Logical Data Independence

Changes in logical schema should not unnecessarily affect applications.

Rule 10 – Integrity Independence

Integrity constraints should be definable independently of applications.

Rule 11 – Distribution Independence

Users should not need to know where data is physically located.

Rule 12 – Nonsubversion

Lower-level access should not bypass relational integrity rules.

33. SQL Joins

Inner Join

Returns matching rows.

SELECT Student.Name, Department.Department_Name
FROM Student
INNER JOIN Department
ON Student.Department_ID = Department.Department_ID;

Left Join

Returns all rows from the left table and matching rows from the right.

Right Join

Returns all rows from the right table and matching rows from the left.

Full Outer Join

Returns matching rows plus nonmatching rows from both sides, where supported.

Part E – Normalization

39. Functional Dependency

A functional dependency describes a relationship between attributes.

Written as:

X → Y

It means:

If two rows have the same value of X, they must have the same value of Y.

Example:

Student_ID → Student_Name

because a Student_ID identifies one student.

40. Types of Functional Dependency

Important concepts:

  • Trivial dependency
  • Non-trivial dependency
  • Full functional dependency
  • Partial dependency
  • Transitive dependency

Trivial Functional Dependency

If:

Y is a subset of X

then:

X → Y

is trivial.

Partial Dependency

A non-key attribute depends on only part of a composite key.

Transitive Dependency

If:

A → B
B → C

then:

A → C

may represent a transitive dependency.

41. Normalization

Normalization organizes tables to reduce redundancy and update anomalies.

Main normal forms:

  • 1NF
  • 2NF
  • 3NF
  • BCNF
  • 4NF
  • 5NF

42. First Normal Form – 1NF

A relation is in 1NF when attributes contain atomic values and repeating groups are removed.

Bad:

Student Phone
Arun 9876, 8765

Better:

Student Phone
Arun 9876
Arun 8765

43. Second Normal Form – 2NF

A relation must:

  1. Be in 1NF.
  2. Have no partial dependency of a non-key attribute on part of a candidate key.

2NF is especially important when the key is composite.

44. Third Normal Form – 3NF

A relation must:

  1. Be in 2NF.
  2. Have no problematic transitive dependency of non-key attributes on a candidate key.

A common simplified rule:

Non-key attributes should depend on the key,
the whole key,
and nothing but the key.

45. BCNF

A relation is in BCNF if every determinant is a candidate key.

BCNF is generally stronger than 3NF.

46. 4NF

4NF deals mainly with multivalued dependencies.

47. 5NF

5NF deals with join dependencies and decomposition that cannot be further improved without introducing problems.

48. Normalization Summary

Normal Form Main idea
1NF Atomic values
2NF Remove partial dependency
3NF Remove transitive dependency
BCNF Every determinant is a candidate key
4NF Remove problematic multivalued dependencies
5NF Deal with join dependencies

50. Query Optimization

Query optimization attempts to find an efficient way to execute a query.

Possible techniques:

  • Selection pushdown
  • Projection pushdown
  • Join ordering
  • Index usage
  • Cost estimation
  • Choosing efficient access paths

Selection Pushdown

Apply filters as early as possible to reduce intermediate data.

Example:

Instead of joining all rows and then filtering:

Join → Filter

try:

Filter → Join

when logically valid.

Part G – Transaction Processing

51. Transaction

A transaction is a logical unit of database work.

Example:

Bank transfer:

Debit Account A
       +
Credit Account B

Both operations should be treated as one logical transaction.

52. ACID Properties

A transaction should satisfy:

A → Atomicity
C → Consistency
I → Isolation
D → Durability

Atomicity

All operations occur or none occur.

Consistency

A transaction takes the database from one valid state to another valid state.

Isolation

Concurrent transactions should not improperly interfere with each other.

Durability

Committed changes should survive failures.

53. Transaction States

Common states:

Active
  |
  v
Partially Committed
  |
  v
Committed

A transaction can also enter:

Failed
  |
  v
Aborted

54. Concurrency Control

Concurrency control manages simultaneous transactions.

Problems without proper control include:

  • Lost update
  • Dirty read
  • Non-repeatable read
  • Incorrect summary
  • Phantom read

55. Locking

A common technique is lock-based concurrency control.

Two basic locks:

Shared Lock

Used for reading.

S-lock

Exclusive Lock

Used for writing.

X-lock

Compatibility:

Existing / Requested S X
S Yes No
X No No

56. Two-Phase Locking

Two-phase locking (2PL) has two phases:

  1. Growing phase
  2. Shrinking phase

Growing Phase

Locks can be acquired.

Shrinking Phase

Locks can be released.

Basic idea:

Growing
Acquire locks
     |
     v
Shrinking
Release locks

57. Timestamp Ordering

Transactions are assigned timestamps.

Operations are ordered according to timestamps to maintain serializability.

58. Deadlock

Deadlock occurs when transactions wait for each other indefinitely.

Example:

T1 holds A → waits for B
T2 holds B → waits for A

This creates a cycle.

Solutions include:

  • Deadlock prevention
  • Deadlock avoidance
  • Deadlock detection
  • Recovery

Part H – Database Recovery

59. Database Recovery

Recovery restores the database to a consistent state after failure.

Failure types:

  • Transaction failure
  • System crash
  • Disk failure

60. Log-Based Recovery

A log records database operations.

Typical information includes:

Transaction
Old value
New value
Operation

Two important concepts:

  • UNDO
  • REDO

UNDO

Reverse changes made by incomplete transactions.

REDO

Reapply changes made by committed transactions when required.

61. Checkpoint

A checkpoint periodically records a known recovery point.

It reduces the amount of log processing needed during recovery.

62. Shadow Paging

Shadow paging maintains alternative page tables so recovery can avoid some forms of log-based processing.

64. Object-Relational Database

An object-relational DBMS combines relational database features with object-oriented features.

Possible features:

  • Complex data
  • Object-like structures
  • Methods

Part J – Database Security and Authorization

65. Database Security

Database security protects data from:

  • Unauthorized access
  • Modification
  • Disclosure
  • Destruction

Security mechanisms include:

  • Authentication
  • Authorization

85. Association Rules

Association mining finds relationships between items.

Example:

Bread → Butter

Important measures:

Support

Support measures how frequently an itemset occurs.

Support(X) =
Number of transactions containing X
------------------------------------
Total number of transactions

Confidence

Confidence(X → Y) =
Support(X ∪ Y)
----------------
Support(X)

Lift

Lift(X → Y) =
Confidence(X → Y)
------------------
Support(Y)

Interpretation:

Lift > 1 → positive association
Lift = 1 → approximately independent
Lift < 1 → negative association

  5. Assign the class.

Important point:

The choice of K affects the result.

101. MapReduce

MapReduce is a distributed processing model.

It has two main conceptual stages:

  |
  v

  |
  v
Shuffle / Sort
  |
  v

  |
  v

Map

Processes input records and produces intermediate key-value pairs.

Shuffle and Sort

Groups intermediate values by key.

Reduce

Processes values belonging to each key and produces final results.

102. Example of MapReduce

Suppose we want to count words.

Input:

cat dog cat

Map:

(cat, 1)
(dog, 1)
(cat, 1)

Shuffle:

cat → [1, 1]
dog → [1]

Reduce:

cat → 2
dog → 1

123. Common Mistakes

Schema vs Instance

Schema   → Structure
Instance → Current data

Primary Key vs Foreign Key

Primary key → Identifies a row
Foreign key → References another table

WHERE vs HAVING

WHERE  → Rows
HAVING → Groups

DELETE vs DROP

DELETE → Removes rows
DROP   → Removes database object such as a table

2NF vs 3NF

2NF → Partial dependency
3NF → Transitive dependency

OLTP vs OLAP

OLTP → Daily transactions
OLAP → Analysis

Classification vs Clustering

Classification → Known classes
Clustering     → Classes/groups discovered from data

NameNode vs DataNode

NameNode → Metadata
DataNode → Actual blocks

Map vs Reduce

Map    → Intermediate key-value pairs
Reduce → Aggregates/processes grouped values
